# システム構成

## データフロー

1. エッジがUSB WebカメラからJPEG画像を約10秒間隔で取得する。
2. エッジがデバイスID、部屋名、画像を`multipart/form-data`でバックエンドへ送る。
3. FastAPIは入力とAPIキーを検証し、処理キューへ入れて`202 Accepted`を返す。
4. バックグラウンドワーカーが人物検出を実行する。
5. ストレージがOSファイルロックを取得し、名称、履歴、最新人数を更新する。
6. PHPはページ要求ごとに統合スナップショットAPIから最新JSONを取得する。
7. PHPが`ID_condition.csv`の閾値から混雑度を判定して表示する。

## CSV

バックエンドのデータディレクトリには次のファイルを置きます。

- `ID_name.csv`: `id,room_name,updated_at`
- `crowded.csv`: `id,person_count,observed_at`
- `each/crowded_01.csv`: `observed_at,person_count`
- `backup/crowded_01_<UTC時刻>.csv`: 部屋名変更前の履歴

CSVはUTF-8です。書き換えは同一ディレクトリ内の一時ファイルを`fsync`した後に`os.replace`し、読み手が途中状態を見ないようにします。全CSVを1つの`.store.lock`で保護するため、名称・最新人数・履歴の更新順序が競合しません。

## 人物検出

検出器は次の3種類です。

- `mock`: 通信・保存・表示の結合確認用。常に0人を返す。
- `random`: エッジから画像を受信するたび、設定範囲内のランダムな人数を返す。
- `yolo`: Ultralytics YOLOのCOCO class 0だけを数える。

`random`の既定範囲は0～30人です。`CROWDED_RANDOM_MIN_COUNT`と`CROWDED_RANDOM_MAX_COUNT`で変更でき、`CROWDED_RANDOM_SEED`を指定すると再起動後も同じ疑似乱数列を再現できます。

画像は推論処理中だけメモリに保持し、現在の実装ではディスクへ保存しません。`mock`と`random`も受信経路の検証対象なので、空画像は拒否します。YOLOモデル、画像解像度、信頼度は実際の画角で評価して調整します。

YOLOモードではAPI起動前に黒画像を1回推論し、CUDAとモデルをウォームアップします。既定の入力サイズは640、ウォームアップ元画像はエッジの標準撮影条件に合わせて1280×720です。`CROWDED_YOLO_IMAGE_SIZE`、`CROWDED_YOLO_WARMUP_WIDTH`、`CROWDED_YOLO_WARMUP_HEIGHT`で変更できます。各観測の処理ログには人物数と推論時間を記録しますが、画像やAPIキーは記録しません。

## 同時実行モデル

FastAPIの受信処理と推論処理は`asyncio.Queue`で分離しています。キュー満杯時はHTTP 503を返し、エッジは次の周期で再試行します。初期版はAPIプロセス内にキューとGPUワーカーがあるため、Uvicornは1プロセスで動かします。

将来、複数GPUや永続キューが必要になった場合は、Redisなどの外部キューとGPUごとの推論ワーカーへ置き換えます。CSVストレージのインターフェースはそのまま利用できますが、規模が増えた場合はSQLiteまたはPostgreSQLへの移行を推奨します。

## フロントエンドからの取得

PHPはバックエンドの2つのCSVを別々にコピーせず、名称と人数を統合したJSONをページ要求ごとに取得します。APIキーはPHPサーバ側だけに保持し、ブラウザには公開しません。フロントエンドではキャッシュ、ロック、一時ファイルを作成しないため、アプリケーションディレクトリへの書込権限は不要です。

バックエンドが一時的に利用できない場合は、古い情報を表示せず「現在、混雑状況を取得できません」と表示します。接続待ちでページ応答が長時間停止しないよう、バックエンド通信には短いタイムアウトを設定します。
